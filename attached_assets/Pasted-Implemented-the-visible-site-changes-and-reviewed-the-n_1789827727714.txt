## ThriveUp/provider-intelligence review

The new material provides a real initial integration surface:

`GET /api/partner/v1/ms/intelligence`

Reported characteristics:

- Requires `health:read`
- Supports nationwide provider discovery
- Separates public and internal-ecosystem visibility
- Includes freshness and catalog-health information
- Includes MS Center, research, health, National MS Society, Medicare, and ClinicalTrials.gov destinations
- Uses query validation and rate limiting
- Restricts internal-only catalog entries
- Rejects malformed AI output
- Reports explicit provider-unavailable states

This is a useful first vertical slice, but it is still **provider intelligence**, not closed-loop care coordination.

The reported response correctly labels leads as:

`cited_ai_lead_not_verified`

It does not yet enable:

- Referral creation
- Referral acceptance
- Scheduling
- Referral status
- Service completion
- Patient outcomes
- Caregiver exchange
- Clinical exchange
- Device exchange
- Research-participant exchange
- Treatment exchange

### Still required before wiring the live consumer

The handoff does not contain:

- ThriveUp base URL
- OpenAPI specification
- Exact response schema
- OAuth issuer or token endpoint
- Audience
- Service-identity provisioning process
- Sandbox identity
- Example successful response
- Example unavailable response
- Rate-limit specification
- Production activation procedure

I did not guess these values or create an adapter against an assumed payload. Once provided, the first integration can consume the catalog through the backend, preserve visibility restrictions, expose freshness and availability honestly, and avoid placing partner credentials in the browser.

## Why

These changes establish the visible application shell needed for the approved architecture while preserving product truth. The navigation can expand as caregiver, clinician, community, research, referral, and IoT/ILT workflows become operational, without advertising them before they work.
