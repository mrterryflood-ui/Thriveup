1) What We’re Measuring and Why

Thrive is not a “risk score”

Thrive is a navigation score that answers:
	1.	How is this student doing right now?
	2.	What’s changing over time?
	3.	What supports should we deploy before a crisis?
	4.	What does “success in the next 30 days” look like?

Key principle: We don’t “predict failure.” We detect drift, identify barriers, and strengthen protective factors.

⸻

2) The Thrive Framework

2.1 Thrive Domains

Each domain outputs:
	•	a 0–100 score
	•	a trend line (improving / flat / declining)
	•	explainable drivers (what moved it)

Domain A — Learning & Engagement

Signals (examples):
	•	Attendance and tardies
	•	Course performance (grade bands, not detailed grades if you want minimal data)
	•	SIM engagement consistency (quests completed, portfolio activity cadence)
	•	On-time milestone completion

Domain B — Executive Function & Decision Quality

Signals:
	•	Reflection quality rubric score
	•	“Revision justification” rubric score (when plans change)
	•	CYOA decision patterns (impulse vs deliberation)
	•	Financial simulation behavior (short-term vs long-term patterns)
	•	“Repair actions” after setbacks (did student recover constructively?)

Domain C — Belonging & Pro-Social Connection

Signals:
	•	House participation / team contributions
	•	Mentor interaction cadence (frequency + completion)
	•	Peer collaboration (competitions, projects)
	•	Help-seeking behavior (requests for guidance)

Domain D — Wellbeing & Stability (Consent-based)

Signals:
	•	Student check-ins (brief, nonclinical, opt-in)
	•	Requests for support (school counselor referral workflows if district allows)
	•	“Energy / stress / focus” self-ratings (light, not diagnostic)

Domain E — Context Load (Place-based)

This is where home life, SES, and SDOH enter without tracking private family details.
We use public data at neighborhood scales (tract/ZCTA) to represent environmental burden:
	•	Social vulnerability
	•	Poverty/unemployment proxies
	•	Housing instability proxies
	•	Local health burden
	•	Community violence exposure proxies

The CDC/ATSDR Social Vulnerability Index is explicitly designed to identify communities that may need additional support and uses a set of census variables to capture social vulnerability.  ￼

Domain F — Protective Factors / Buffering

This is the counterweight to risk.
Signals:
	•	Stable adult connection strength (advisor + mentor consistency)
	•	Activity anchors (clubs, service, consistent routines)
	•	Portfolio momentum (evidence of follow-through)
	•	Community contribution (service logs)
	•	“Positive identity reinforcement” activities (leadership roles)

⸻

2.2 Thrive Outputs

Student Level
	•	Thrive Score (current)
	•	Thrive Trajectory (30/60/90-day slope)
	•	Early Warning Flags (Watch / Support / Stabilize)
	•	“Next Best Actions” (advisor/mentor actions tied to triggers)

Population Level
	•	Cohort heatmaps of context load and protective factor coverage
	•	Mentor density maps (who is under-supported)
	•	Milestone completion distributions by geography
	•	Equity checks (are some neighborhoods systematically under-resourced?)

3) Data Sources for GIS + Public Context Layering

You asked for: crime + public health + other public data, layered.

Below is a practical, defensible baseline stack (with sources you can automate).

3.1 Public Health Data

CDC PLACES (local health indicators)

PLACES provides local estimates for health outcomes, risk behaviors, and prevention measures and is accessible via API (Socrata) for further analysis and GIS use.  ￼
There are GIS-friendly PLACES datasets (e.g., county GIS format releases) hosted on CDC’s open data platform.  ￼

CDC WONDER (mortality and other datasets via API)

CDC WONDER supports automated data queries via an API web service.  ￼
Note: WONDER also indicates modernization changes are coming, so we architect a “data connector” that can adapt.  ￼

3.2 Social Determinants / Vulnerability

CDC/ATSDR Social Vulnerability Index (SVI)

SVI provides tract-level vulnerability; and the SVI 2022 update includes ZIP Code Tabulation Area (ZCTA) data, which is extremely useful for district operational mapping.  ￼
SVI is also positioned for planning and resource allocation—exactly your Thrive use case.  ￼

3.3 Crime / Public Safety Data

FBI Crime Data Explorer + Crime Data API (UCR)

The FBI Crime Data API is a read-only service returning JSON/CSV UCR data and is accessible through the Crime Data Explorer documentation.  ￼
The FBI also notes that UCR data is released quarterly on CDE.  ￼
(For local fidelity, you’ll also ingest city/county open data for calls-for-service where available.)

4) Student-Level GIS Without Surveillance

This is where systems either become brilliant or unethical.

4.1 What we store

We do not need to store exact home addresses.

Preferred:
	•	Census tract ID, ZCTA, or a geohash at reduced precision
	•	Or distance bands (0–2mi, 2–5mi, etc.) from school

This lets us link a student to public neighborhood layers without exposing sensitive location.

4.2 What students/parents see vs what staff see
	•	Students: strengths, goals, resources, progress, reflections
	•	Parents: progress + notifications + resource links
	•	Teachers/advisors: support-oriented insights and action steps
	•	Admins: population analytics + resource allocation views

No one sees “labels.” They see “supports needed” and “actions recommended.”

5) The Early Warning System

Explainable + IGN-aligned

5.1 Trigger Types

Trigger Class 1 — Engagement Drift
	•	drop in weekly activity completion
	•	plateau in portfolio updates
	•	sharp decline in attendance proxies

Trigger Class 2 — Decision Pattern Risk (SIM-based)
	•	repeated “impulsive spend” behaviors without reflection improvement
	•	repeated pathway revision attempts without justification quality
	•	CYOA decisions clustering in high-risk themes without repair behaviors

Trigger Class 3 — Context Shock (GIS-based)
	•	neighborhood-level public safety trend shifts
	•	health burden proxies rising (where data cadence allows)
	•	disruption markers (seasonal spikes, locality events)

5.2 Flag Levels

Watch: light drift → Spark + advisor nudge
Support: drift persists → advisor session + mentor check-in
Stabilize: multiple domains declining → coordinated support plan

5.3 Every flag must produce a “4-Part Explainable Card”
	1.	What changed (signal)
	2.	Why it might matter (hypothesis)
	3.	What we do next (navigation action)
	4.	30-day success target (SMART)

No black boxes. No “risk score” scare tactics.

7) Scoring & Thresholds

Transparent and tunable

7.1 Composite Thrive Score (example)
	•	A Learning/Engagement: 25%
	•	B Decision Quality: 20%
	•	C Belonging: 15%
	•	D Wellbeing: 10% (only if available; otherwise redistributed)
	•	E Context Load: 15% (context, not blame)
	•	F Protective Factors: 15%

Important: Context Load should influence navigation urgency and resource linkage, not student penalties.

7.2 “Change detection” is the real engine

You don’t flag a kid for a low score.

You flag when:
	•	slope turns down
	•	multi-domain decline emerges
	•	protective factors are absent
	•	revision behavior becomes reactive

8) IGN Embedded Throughout the Platform

This is the “throughout” requirement you stated.

8.1 In curriculum

Every unit ends with:
	•	action → consequence → reflection → adjustment

8.2 In revisions
	•	no changes without justification
	•	no justification without guidance (advisor)
	•	parent notified always

8.3 In Spark AI

Spark never chooses for students. Spark navigates:
	•	comparison prompts
	•	consequence previews
	•	reflective questions
	•	repair options
	•	resource suggestions

8.4 In mentorship

Mentor sessions follow a structured “navigation script,” not casual chats:
	1.	What are you trying to achieve right now?
	2.	What tradeoffs do you see?
	3.	What assumptions are you making?
	4.	What’s one action this month?
	5.	What support do you need?

8.5 In dashboards

Dashboards don’t say: “High risk student.”
They say: “Student needs more buffering and navigation; here’s what changed; here’s the plan.”

9) Barriers, ACEs, Risk/Protective Factors

What gets included and how

9.1 Barriers

We incorporate:
	•	home life stressors (through student-reported needs + place-based proxies)
	•	SES and SDOH (place-based data, not invasive personal data)
	•	risk factors (context load + drift patterns)
	•	protective factors (mentor density, belonging, stability routines)

9.2 ACEs

ACEs are included as:
	•	a staff training lens
	•	a scenario design lens (CYOA reflects realistic adversity)
	•	a protective factor strategy (stable adult connection is core)

ACEs do not become a badge, label, or algorithmic identity.
