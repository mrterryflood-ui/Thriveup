What the Ecosystem Already Has — So We Don't Ask for What We Already Have
Before giving you the requirements list, here's what's already connected to ThriveUp's API and working:

Already Live	Endpoint
Heartbeat + fidelity scoring	POST /api/ecosystem/heartbeat
Event send (referrals, user_connected, crisis_alerts)	POST /api/ecosystem/event
Directives + acknowledgment	GET/POST /api/ecosystem/directives/...
ThriveUp AI query (proxied on our server)	POST /api/ecosystem-ai/query
Incoming events handler	(heartbeat response pendingEvents)
Auth	x-ecosystem-key header, ECOSYSTEM_API_KEY env var
We also already handle incoming event types: crisis_alerts, cross_platform_referral, provider_referral, resource_referral, condition_viewed, community_health_data, case_management_updates.

The mesh and the handshake are solid. What's missing is data endpoints — the specific resource and SDOH data layers that ThriveUp holds.

What We Need From ThriveUp's API
Block 1 — Location-Based Benefits Navigation
Powers: replacing our static financial navigator with live, location-aware data

GET /api/benefits/lookup
  Query params:
    - zip: string          (e.g. "78753" — Austin East)
    - state: string        (e.g. "TX")
    - programs: string[]   (e.g. ["WIC","medicaid","SNAP","CHIP","TANF","LIHEAP"])
    - population: string   (e.g. "pregnant" | "postpartum" | "general")
Response shape we need:
  {
    zip: string,
    state: string,
    programs: [
      {
        name: string,           // "WIC"
        eligibilityUrl: string,
        enrollmentPhone: string,
        localOffices: [{ name, address, phone, hours }],
        incomeThreshold: string,
        coverageNotes: string   // e.g. "Covers through 12 months postpartum"
      }
    ]
  }
Why: When a BMV mother asks "how do I get WIC in Austin" — instead of sending her to a static page, we query this and surface her nearest WIC office with hours and phone, in context.

Block 2 — City/County/ZIP SDOH Data
Powers: condition pages, the health equity map, and the Austin Black Maternal Health page

GET /api/sdoh/location
  Query params:
    - fips: string         (county FIPS code, e.g. "48453" for Travis County)
    - zip: string          (optional, for sub-county)
    - metrics: string[]    (e.g. ["maternal_mortality","prenatal_access","food_insecurity",
                                   "uninsured_rate","social_vulnerability_index",
                                   "transportation_access","broadband_access"])
Response shape we need:
  {
    location: { fips, county, state, zip? },
    metrics: {
      maternal_mortality_rate_per_100k: number,
      maternal_mortality_black_rate: number,
      prenatal_care_first_trimester_pct: number,
      prenatal_care_desert: boolean,
      food_insecurity_rate: number,
      uninsured_women_pct: number,
      social_vulnerability_index: number,   // CDC SVI 0–1
      transportation_access_score: number,
      broadband_access_pct: number
    },
    dataYear: string,
    sources: string[]
  }
Why: Our sdoh.ts has state-level data for all 50 states. ThriveUp has city/county/zip. When someone says "I'm in Austin" — we should surface Travis County maternal mortality rates and the prenatal care desert map, not Texas state averages.

Block 3 — Community Resource Directory (Location-Aware)
Powers: the Austin Black Maternal Health page, the provider hub, and warm handoffs to BMV

GET /api/resources/community
  Query params:
    - zip: string
    - radius_miles: number   (default 25)
    - types: string[]        (e.g. ["FQHC","doula","CHW","midwife",
                                     "maternal_health_org","peer_navigator",
                                     "mental_health","food_bank","housing"])
    - population: string     (e.g. "Black_maternal" | "postpartum" | "general")
    - languages: string[]    (optional, e.g. ["en","es"])
Response shape we need:
  {
    resources: [
      {
        id: string,
        name: string,
        type: string,
        address: string,
        phone: string,
        website: string,
        accepts_medicaid: boolean,
        sliding_scale: boolean,
        languages: string[],
        population_focus: string[],   // e.g. ["Black women", "postpartum"]
        description: string,
        distance_miles: number
      }
    ],
    total: number
  }
Why: This replaces our static provider hub with live, location-scoped resources. For BMV specifically — if we register Black Mamas Village as an organization in ThriveUp's directory, Cierra's org surfaces automatically when any HerHealth user searches Austin maternal resources.

Block 4 — Community Partner / Referral API
Powers: BMV as a structured referral origin in the ecosystem

POST /api/partners/referral
  Body:
    {
      fromOrg: string,          // "black-mamas-village"
      toplatform: string,       // "herhealth" | "yourhealthbirthright"
      referralType: string,     // "maternal_health" | "postpartum" | "chronic_condition"
      context: {
        zip: string,
        conditions: string[],   // e.g. ["postpartum-depression", "hypertension"]
        gestationalWeek?: number,
        postpartumWeeks?: number,
        languagePref: string,
        urgency: "routine" | "urgent" | "crisis"
      },
      anonymousId: string       // no PII — just a tracking token
    }
Response shape we need:
  {
    referralId: string,
    routedTo: string,           // which platform received it
    landingUrl: string,         // deep link with context pre-loaded
    status: "accepted"
  }
Why: This is the mechanism that makes BMV a participant instead of a consumer. Cierra's CHWs submit a referral from their side of ThriveUp, it hits this endpoint, our ecosystem.ts handleIncomingEvent catches the cross_platform_referral event, and the mother lands on HerHealth (or YourHealthBirthright) with her context already loaded — no re-entry.

Block 5 — Organization Registry
Powers: verifying BMV is in ThriveUp's directory and registering new partners

GET /api/orgs/:orgId
  Response: { id, name, type, zip, phone, website, programs[], focusPopulations[] }
POST /api/orgs/register  (or confirm BMV is already in ThriveUp)
  Body: { name, type, zip, focusPopulations, programs, contactEmail, contactPhone }
Why: Before we build the BMV referral flow, we need to confirm Black Mamas Village is registered in ThriveUp's org registry. If they're not, we submit them. Once they're in, the community resource directory query (Block 3) surfaces them automatically.

Block 6 — Outcomes / Referral Status Tracking
Powers: the research dataset and grant narrative

POST /api/outcomes/checkin
  Body:
    {
      referralId: string,
      platformId: "herhealth",
      checkInWeek: number,      // 1, 4, 8, 12, 24, 52
      anonymousId: string,
      conditionsTracked: string[],
      engagementEvents: string[], // ["screener_completed","nia_session","resource_clicked"]
      outcomeFlags: {
        connectedToCare: boolean,
        benefitsEnrolled: boolean,
        screenerCompleted: boolean,
        peerNavigatorConnected: boolean
      }
    }
GET /api/outcomes/aggregate
  Query: platformId, dateFrom, dateTo, zip?, condition?
  Response: anonymized aggregate engagement + outcome rates
Why: Every referral that comes from BMV should close a loop. 30/60/90 days later, the platform checks back. That aggregate data is the research dataset — it's what makes the NIH D&I grant narrative real, not hypothetical.

What We're Sending Back (So ThriveUp's API Team Knows Both Sides)
We already send these events to ThriveUp on every relevant action. They should expect:

cross_platform_referral     — when we route a user to YourHealthBirthright or Sankofa Mind
user_connected              — confirmation that a ThriveUp referral was received
resource_recommendations    — when Nia surfaces external resources
behavioral_assessments      — when a screener is completed (EPDS, autoimmune, endometriosis)
community_health_data       — aggregate SDOH engagement data
network_connection_established — on every server startup
