## What exists
- `server/orchestration/engine-registry.ts` — manifest of platform engines with domain/geography-grain/PII/operatorSelectable tags.
- `server/orchestration/conductor.ts` — `getOrchestratedIntelligence(geo, {engines?, domains?, collegeAccessQuestion?, collegeAccessStudentProfile?})` calls relevant engines in parallel, returns provenance-tagged bundle.
- Wired into `queryRAG` (both non-streaming and streaming paths) in `server/rag-engine.ts` — geography auto-detected from a ZIP mentioned in the user's query.
- **All 25 registered engines are now function-callable in-process** (`IN_PROCESS_ENGINE_IDS` in `conductor.ts` includes every registry id). 24 of them are aggregate/dataset-backed and eligible for default-pool or domain-bundle auto-inclusion (see prior sessions' notes below for the join patterns). The 25th, **college-access-ai**, is wired but deliberately kept out of the default pool and domain-bundle auto-inclusion — see "operatorSelectable" below.
- **operatorSelectable engine pattern (new this session)**: `EngineDefinition.operatorSelectable?: boolean` on the registry. An engine with `operatorSelectable: true` AND `touchesPII: true` is excluded from `getNonPIIEngines()` pool and from `domains`-based bundling, but CAN fire if — and only if — an operator names it explicitly via `options.engines` AND supplies its required payload (for college-access-ai: `options.collegeAccessQuestion`, a non-empty string). Naming the id alone does NOT bypass the wall; the payload presence is the actual consent/authorization check, done in `getOrchestratedIntelligence()`'s selection step, re-checked defensively inside `callEngine()`. This is the correct pattern for wiring in a *live, question-scoped* AI advisor with no backing dataset — never for an engine that reads a stored PII table (that must stay `operatorSelectable: false`/absent, aggregate-only, per the existing pattern below).
- **Conductor-side AI spend cap**: `CONDUCTOR_AI_CALL_LIMIT = 5` operator-invoked AI calls per minute, process-wide (`checkConductorAiCallBudget()` in `conductor.ts`). This is separate from and in addition to the per-IP HTTP rate limiter already in `college-access-ai-routes.ts` (`AI_ADVISOR_RATE_LIMIT = 10/min/IP`) — operator/collaborative calls go through `getOrchestratedIntelligence()` directly and never touch that HTTP path, so the route-level limiter can't see them. Real, verified via a live test call in this session (single OpenAI response returned; Claude/Gemini/DeepSeek engines failed/timed out on this run per usual collaborative-ai multi-engine behavior, unrelated to this feature).
- Verified via direct test script covering all 4 branches: (1) default no-filter pool excludes college-access-ai, (2) `domains: ["education","youth"]` bundle excludes it, (3) explicit `engines: ["college-access-ai"]` with no question is skipped with an explicit reason, (4) explicit `engines: ["college-access-ai"]` + `collegeAccessQuestion` fires a real `collaborativeResponse()` call and returns a real answer.
- **All 24 dataset-backed engines** (from prior sessions): chainweb-engine, gis-engine, equity, benefits, corridor-chainweb, scorecard, corridor-story, farmworker-iti, reentry, resident-journey, regional-briefing, rural-health, rural-workforce, rural-housing, neighborhood, safe-passage, farm-cooperative, farm-profitability, foster-youth-agency, workforce, justice, trade-sims, clinical, rural-connectivity (rural-connectivity is PARTIAL — only `getServiceDesertScore()` is wired; FCC broadband/cell-coverage sub-features still need real lat/lng that `GeographyRef` doesn't carry and no county-centroid table exists to derive one without fabricating a point).
- Small-cell suppression helper `suppressSmallCells()` (floor `MIN_AGGREGATE_CELL = 5`) applied to workforce/justice/trade-sims/clinical count-aggregate branches; clinical additionally guards on total-below-floor.
- **Pattern for wiring a PII-table engine as aggregate-safe**: join down to just the geography key + the one non-identifying field being counted/grouped, filter to the target county/state, GROUP BY + COUNT — never select(`*`) or any name/contact/notes column. Document in the registry `notes` field exactly which columns the aggregate touches and which raw sensitive columns exist on the underlying table but are never selected, so a future edit that "helpfully" widens the select doesn't silently break the PII wall (registry `touchesPII: false` is a claim about the *query path*, not the *table*).
- **ZIP→county nationwide resolution is solved.** `zctaCountyMap` DB table loaded from the Census ZCTA-County relationship file via `scripts/load-zcta-county.ts` (idempotent). `server/geo/zip-county-resolver.ts` exposes `resolveZipBestEffort()`: DB lookup first, static fallback table second.
- Instrument picker has a real UI: `client/src/pages/ecosystem-ai.tsx` domain-toggle chips pass `domains` to `POST /api/ecosystem-ai/stream`. A separate "College & FAFSA Advisor" toggle + question textarea now exists alongside it — when enabled it sends `engines: ["college-access-ai"]` + `collegeAccessQuestion` instead of `domains`, mutually exclusive with the domain picker for that message. The `/api/ecosystem-ai/stream` route synthesizes an inert placeholder `GeographyRef` when a college question is present but no ZIP was found in the query text, since `getOrchestratedIntelligence()` requires a geo argument to run at all even though the college-access-ai branch never reads it.

## Safety notes
- `touchesPII: false` on an ENGINE_REGISTRY entry is a per-*engine-query-path* label, not a per-*table* guarantee. Several engines sit on top of tables that are genuinely PII-bearing at the row level — wall-safe only because the specific conductor branch selects nothing but a geography key + one non-identifying field for a COUNT/GROUP BY, with small-cell suppression. Always open the actual table definition before wiring or widening a query.
- `operatorSelectable: true` must ONLY be set alongside `touchesPII: true` for engines with NO stored dataset — a live, per-request, question-scoped advisor where the explicit id+payload pair from an operator is itself the authorization event. Never set it on an engine that would otherwise scan a stored PII table; that must stay aggregate-only per the pattern above, not operator-selectable.

## Hard constraints discovered (do not re-attempt without new info)
- FCC broadband-availability and cell-coverage lookups inside rural-connectivity need real lat/lng; `GeographyRef` doesn't carry coordinates and no county-centroid table exists.

## Why this matters
The project's whole culture is anti-fabrication (Iron Rule #2, #10, #11) — an orchestration/audit claim that isn't actually backed by a working code path or a real test run is a project-level trust violation here, not just a bug.

## How to apply
Before extending the Conductor to a new engine, check `IN_PROCESS_ENGINE_IDS` in `conductor.ts` — if the target engine isn't in that list, either add a genuine function-call path or an internal-fetch-to-its-own-route path; don't fake a result. Before declaring a new engine "blocked," trace the FULL join graph in `shared/schema.ts`, not just the immediate table's own columns. For any live-AI/no-dataset engine, use the operatorSelectable pattern above rather than either force-fitting it into the aggregate-count pattern or leaving it un-wired.
