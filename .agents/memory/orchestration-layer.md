## What exists
- `server/orchestration/engine-registry.ts` — manifest of platform engines with domain/geography-grain/PII tags.
- `server/orchestration/conductor.ts` — `getOrchestratedIntelligence(geo, {engines?, domains?})` calls relevant engines in parallel, returns provenance-tagged bundle.
- Wired into `queryRAG` (both non-streaming and streaming paths) in `server/rag-engine.ts` — geography auto-detected from a ZIP mentioned in the user's query.
- **19 of 25 registered engines are now wired in-process** (`IN_PROCESS_ENGINE_IDS` in `conductor.ts`): chainweb-engine, gis-engine, equity, benefits, corridor-chainweb, scorecard, corridor-story, farmworker-iti, reentry, resident-journey (prior session), plus **regional-briefing** (calls `loadRpliceContextBlock([countyFips])` directly), **rural-health** (calls exported `getHpsaData`+`getRuralHospitalContext`), **rural-workforce** (calls exported `getAgWageData`), **rural-housing** (calls exported `getHousingCostBurden`), **neighborhood** (calls exported `fetchZctaData`, requires a ZIP not just a county), **safe-passage** (new `getListingsForCounty()` helper filters in-memory listings by county and strips notes/phone/address/name — safe by construction, not by aggregation), **farm-cooperative** (aggregate COUNT-by-farmType over `producerProfiles`, matched on stateFips+countyFips), **farm-profitability** (aggregate COUNT-by-commodity over `farmProfitabilitySnapshots`), **foster-youth-agency** (aggregate COUNT-by-placementType over `fosterYouthAgencyCases`, matched on stateCode only — this table has no county column, state-level grain). All verified via direct in-process test calls returning real data (zero-count results for tables with no seed rows are honest empty results, not wiring bugs).
- **Pattern for wiring a PII-table engine as aggregate-safe**: join down to just the geography key + the one non-identifying field being counted/grouped, filter to the target county/state, GROUP BY + COUNT — never select(`*`) or any name/contact/notes column. Document in the registry `notes` field exactly which columns the aggregate touches and which raw sensitive columns exist on the underlying table but are never selected, so a future edit that "helpfully" widens the select doesn't silently break the PII wall (registry `touchesPII: false` is a claim about the *query path*, not the *table* — see Safety note below).
- **Genuinely blocked, confirmed via schema inspection, do not re-attempt without a real schema change**: `workforce` (`workforceAssessments` has no zip/county/state column anywhere), `justice` (`justiceReferrals`/`supervisionCompliance` same), `clinical` (`clinicalScreenings` in `shared/clinical-schema.ts` same, and is the platform's highest-sensitivity table), `trade-sims` (no geography column at all, per-learner data), `college-access-ai` (no backing DB table — it's a live per-request AI advisor, not a queryable dataset), `rural-connectivity` (needs lat/lng, which `GeographyRef` doesn't carry — only county/zip/state; needs a centroid lookup added first). These 6 correctly surface either a PII-wall skip or an explicit error string in the orchestration bundle rather than being silently omitted.
- **ZIP→county nationwide resolution is solved.** `zctaCountyMap` DB table loaded from the Census ZCTA-County relationship file via `scripts/load-zcta-county.ts` (idempotent). `server/geo/zip-county-resolver.ts` exposes `resolveZipBestEffort()`: DB lookup first, static fallback table second.
- Instrument picker has a real UI: `client/src/pages/ecosystem-ai.tsx` domain-toggle chips pass `domains` to `POST /api/ecosystem-ai/stream`.
- Pattern for adding a new DB-backed engine: check the table has a `countyFips`/`zipCode`/`stateCode` column (or a join path to one) in `shared/schema.ts` before wiring — if there is none anywhere in the join graph, that's a real schema blocker, not a quick win; report it as blocked rather than fabricating a join.

## Safety note discovered while wiring engines
`touchesPII: false` on an ENGINE_REGISTRY entry is a per-*engine-query-path* label, not a per-*table* guarantee. Several engines (benefits, farm-cooperative, farm-profitability, foster-youth-agency) sit on top of tables that are genuinely PII-bearing at the row level (name/phone/email/case-ID/mental-health-flag columns) — the engine is only wall-safe because the specific conductor branch selects nothing but a geography key + one non-identifying field for a COUNT/GROUP BY. Always open the actual table definition in `shared/schema.ts` and check for identifying columns before wiring or widening a new query, regardless of what the registry currently says.

## Hard constraints discovered (do not re-attempt without new info)
- ~~No free ZIP-only geocoding API exists~~ — resolved, see above.
- The 6 engines listed above as "genuinely blocked" all require either a schema change (add a geography column) or a product/policy decision (clinical data aggregation) — not a resolver or a quick wiring fix. Re-verify with `rg` against the live schema before assuming this is still true in a future session, since schema changes could resolve some of these later.

## Why this matters
The project's whole culture is anti-fabrication (Iron Rule #2, #10, #11) — an orchestration/audit claim that isn't actually backed by a working code path or a real test run is a project-level trust violation here, not just a bug.

## How to apply
Before extending the Conductor to a new engine, check `IN_PROCESS_ENGINE_IDS` in `conductor.ts` — if the target engine isn't in that list, either add a genuine function-call path or an internal-fetch-to-its-own-route path; don't fake a result.
