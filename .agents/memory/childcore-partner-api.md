## Credential model (two separate keys, never shared)

| Direction | Secret name | Whose key it is | Where it lives |
|---|---|---|---|
| ThriveUp → ChildCORE (outbound) | `CHILDCORE_API_KEY` | Generated by ChildCORE, given to ThriveUp | ThriveUp Replit Secrets |
| ChildCORE → ThriveUp (inbound) | `THRIVEUP_API_KEY` | Stored on ThriveUp, given to ChildCORE | ThriveUp Replit Secrets + ChildCORE's settings |

**Why separate keys:** Each platform generates and controls its own credential. `CHILDCORE_API_KEY` authenticates ThriveUp's outbound calls to ChildCORE's API. `THRIVEUP_API_KEY` is the credential ChildCORE sends when calling ThriveUp's Partner API.

## ChildCORE API

- Base URL: `https://useful-viper-536.convex.site/api/v1`
- Auth: `Authorization: Bearer <CHILDCORE_API_KEY>` OR `X-ChildCORE-Key: <CHILDCORE_API_KEY>`
- `/ping` — unauthenticated health check (returns `{"status":"ok","service":"ChildCORE Partner API","version":"1.0.0"}`)
- Authenticated endpoints currently return 403 → key needs community-scope grant on ChildCORE's admin side

## Known ChildCORE API behaviour

- 401 = no key sent
- 403 with `"FORBIDDEN"` = key authenticated but not scoped for this endpoint (community data requires explicit scope grant in ChildCORE admin)
- Ping WITH the key returns 200 — key format is accepted, just missing data scope
- `cck_live_...` is ChildCORE's issued key prefix; `CHILDCORE_API_KEY` may use a different format if ChildCORE generates it differently

## ThriveUp integration points

- `server/childcore-connector.ts` — outbound connector: transport, probe (now verifies auth too), community data pull, AI context block builder, push to ChildCORE
- `server/childcore-routes.ts` — `/api/childcore/*` routes
- `server/routes.ts` — registers ChildCORE router at `/api`
- `server/rplice-intelligence.ts` — 4th parallel source in `buildCommunityAIContextWithStatus`; `sources.childcore` field on `CommunityAIContextResult`
- `server/partner-api-routes.ts` PINNED array — auto-provisions `THRIVEUP_API_KEY` as ChildCORE's inbound key on every boot (scopes: `community:read, impact:read, inbound:write`, `requireTcafPrefix: false`)
- `server/grantpathpro-routes.ts:1580` — timeout fallback includes `childcore` field

## Probe behaviour

`/api/childcore/ping` now returns `{ ok, reachable, authenticated, latencyMs, configured }`.
- `ok: true` requires BOTH reachable AND authenticated — fails closed
- Homepage badge shows "Unavailable" (not "Live") when `ok: false`

## Inbound auto-provisioning

On every boot, if `THRIVEUP_API_KEY` is set and not already in `partner_api_keys`, the server inserts it as ChildCORE's inbound key. The `requireTcafPrefix: false` flag allows non-`tcaf_` formatted keys. Startup log: `[PartnerAPI] Auto-provisioned pinned key for ChildCORE (...)`.

## Ops Center shortcut

Ops Center → Partner API → "Generate ChildCORE Key" button pre-fills the key creation form with ChildCORE's name and correct scopes.

**How to apply:** When adding new community-intelligence surfaces, call `getChildCORECommunityData(zip)` and append `buildChildCOREContextBlock(data)` to the AI context. When ChildCORE's scope is granted, `sources.childcore` will flip to `"available"` automatically.
