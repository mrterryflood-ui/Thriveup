# Session — 2026-08-28 — Community Events archive concurrency

## Scope

Task 341: keep archived Community Events records permanently read-only during
simultaneous updates.

## Observation

The event mutation routes performed an archive check before entering their write
transactions. An archive could therefore race an event or child mutation after
that check.

## Changed

All event, attendance, need, action, and story write transactions now lock the
organization-scoped parent event row and re-check its status while holding the
lock. Archive itself locks and rechecks the parent before transitioning and
writing its audit entry. Child update/delete paths lock the child then the
parent consistently.

The focused verifier now creates a disposable race event and uses two direct
PostgreSQL transactions to prove that a waiting mutation observes `archived`
after the archive transaction commits. The same verifier also exercises the
live archive endpoint and post-archive `409` endpoint behavior on the primary
event.

## Proof

- `npx tsx scripts/verify-nonprofit-events.ts` passed, including the
  transactional race proof and archived write rejection.
- `NODE_OPTIONS=--max-old-space-size=8192 npx tsc --noEmit -p .` passed with
  zero TypeScript errors.
- `git diff --check` passed.
- The application workflow is running after restart.

## Limit

The preview harness serialized the two HTTP race participants before the second
request reached Express, so the deterministic race proof uses direct PostgreSQL
transactions rather than claiming a browser-mediated concurrency proof.

## Publish migration repair

Publish reported that the legacy event-workspace access foreign key could not
reference `organization_members(org_id, user_id)`. The parent had only a
standalone unique index, not the table `UNIQUE` constraint PostgreSQL requires
for a composite foreign-key target.

The shared schema now models the parent pair as a named `UNIQUE` constraint.
The new forward migration upgrades the pre-existing unique index into that
constraint when present, or creates it otherwise; the historical access
migration defensively establishes the same prerequisite for fresh databases.
Startup applied the forward migration. A rollback-only replay of the exact
failing `ALTER TABLE ... ADD CONSTRAINT ... FOREIGN KEY` statement completed
successfully, preserving development data.

The same idempotent repair is now also invoked through the project's
post-merge migration hook, preventing a future merge from leaving the
development schema in the old index-only state before a Publish attempt.

  child-table truncation fails closed.
