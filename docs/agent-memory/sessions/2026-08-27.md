## Connecticut equity-loss geography alignment

- **Decision:** County-equivalent geography changes require an authoritative
  FIPS/crosswalk resolver at every source-access path. Connecticut's
  legacy-source tracts resolve through the Census
  legacy-county/town → Planning Region → 2022 tract → 2010 USALEEP tract
  chain; a display-name match is not valid evidence.
- **Safety boundary:** A source tract that maps to more than one current
  Planning Region is excluded. No copying, averaging, or allocation is
  permitted without a source-supported rule. An unavailable crosswalk or
  unproven Planning Region remains source-unavailable.
- **Coverage semantics:** Analytical coverage is not deployment coverage.
  Reporting must separately describe states, D.C., territories, and record
  availability (present, usable, source-unavailable, otherwise
  suppressed/incomplete, and missing/unattempted). A jurisdiction is wholly
  source-unavailable only when every expected record is present and has that
  reason.
- **Observed development evidence:** The completed batch tested here has
  3,233 present county-equivalent records, 2,721 usable records, no failed
  county computations, and all nine Connecticut Planning Regions resolve
  without statewide source-coverage loss. The live resolver examined 783
  Connecticut source tracts, uniquely resolved 775, and excluded eight
  boundary-spanning tracts; no malformed identifier appeared in the live
  source.
- **Verification:** Zero-error TypeScript; 35 access-model checks; five
  focused alignment/coverage tests; nine nationwide checks; 58 API checks;
  direct route screenshot; six clean independent audit domains; and an
  approved independent architect review. A platform-wide completion run had
  two unrelated youth-mode response waits time out under concurrent
  validation, but an immediately repeated, lock-protected youth-mode run
  passed all five flows without a code change.
- **Residual:** The Replit development proxy returned HTTP 502 after three
  browser-test retries while the application listened on `0.0.0.0:5000` and
  answered locally. Direct preview capture rendered the report; proxy-based
  interactive browser proof remains an environment limitation and is logged
  in the residual ledger. These are development-only observations, not
  production verification.


## Organization event-workspace staff authorization

- **Decision:** Private Community Events access remains a two-part decision:
  an approved persisted platform-staff role and an approved active
  organization membership role. An organization owner may manage only the
  narrow `member` ↔ `staff` membership transition for an existing
  same-organization member who already satisfies the platform-staff check.
- **Safety boundary:** The client sends only a target user ID. The server
  derives organization and actor from the authenticated request, locks and
  rechecks owner/target authorization inside one transaction, conditionally
  changes the exact expected membership state, and creates an audit witness
  only after that change succeeds. Collaborators, ordinary members, foreign
  targets, repeated requests, and broader organization roles all fail closed.
- **Audit decision:** Workspace-access history is a dedicated append-only
  table with opaque IDs, action, fixed role, and server timestamp only.
  Direct update, delete, and truncate are blocked; organization deletion may
  perform referential cleanup. Owner-facing audit responses omit actor,
  subject, event, story, contact, and free-text content.
- **Observed development evidence:** The new migration applied during
  startup. The focused live verifier passed broad-role member and
  collaborator denial, owner management without event-data permission,
  grant-to-access, revoke-to-denial, cross-organization rejection, strict
  payload rejection, no-audit-on-failure, and audit immutability. Full
  auth regression passed 32 browser tests plus all chained checks; strict
  TypeScript passed with zero errors. The formal preflight passed all nine
  checks and memory health passed all eight checks.
- **Residual:** The Replit proxy host returned 502 before an authenticated
  browser session could load this panel. Local preview rendering, live API
  proof, the focused verifier, and the full auth gate are development
  evidence only; the proxy limitation remains tracked in the shared
  residual ledger. Separate legacy event concurrency and event-audit
  findings are also recorded there rather than conflated with this feature.

## Composite event foreign-key publish failure

- **Finding:** The next publish attempt failed while adding
  `fk_nonprofit_event_actions_event_org`: PostgreSQL could not find a matching
  unique key for the parent columns `(nonprofit_events.id, nonprofit_events.org_id)`.
- **Root cause:** The parent-side composite key existed only as a redundant
  standalone unique index in a hand-written SQL file. The publish diff omitted
  that index because `id` is already the primary key, while the Drizzle schema
  still generated composite child foreign keys.
- **Changed:** Declared `UNIQUE (id, org_id)` in the Drizzle schema as a real
  table constraint. Updated the integrity migration to convert the existing
  development index into that constraint when present, or create the
  constraint directly when absent. The regression gate now checks the live
  parent constraint.
- **Proof:** The generated development-to-production diff now emits
  `CONSTRAINT "nonprofit_events_id_org_unique" UNIQUE("id","org_id")` inside
  `CREATE TABLE "nonprofit_events"` before the child composite foreign keys.
  The diff reports `structuralDataLoss: false`; the nonprofit-event regression
  and TypeScript checks pass.
- **Boundary:** The production overwrite option is not required for this fix
  and would replace all production data with development data. No production
  database was changed.

- **Upgrade-path repair:** Because applied migrations are tracked by filename,
  an edited historical migration cannot repair an environment that already
  recorded it. Added the new forward migration
  `20260905_nonprofit_events_composite_key_repair.sql`; application restart
  applied it successfully in development.
- **Final proof:** The startup migration ledger contains the privacy migration,
  integrity migration, and new repair migration. The generated publish diff
  emits the real parent UNIQUE before all four composite child FKs and reports
  `structuralDataLoss: false`. Event regression, TypeScript, preflight,
  memory-health, and application startup checks pass.
- **Audit closure:** The verifier now queries all parent-referencing foreign
  keys on the four event child tables and requires exactly the four intended
  child/table mappings, `(event_id, org_id)`, and `ON DELETE CASCADE`; extra or
  scalar relationships fail the gate.
